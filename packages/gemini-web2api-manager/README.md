# gemini-web2api-manager

OpenAI-сумісний шлюз до Gemini на базі [gemini-web2api](https://github.com/Sophomoresty/gemini-web2api). Акаунти беруться
із зашифрованого сховища [`gemini-vault`](../gemini-vault); коли в поточного акаунта закінчується ліміт, шлюз повторює
запит на іншому — клієнт нічого не помічає.

## Встановлення

```bash
pip install "gemini-web2api-manager @ git+https://github.com/CatDogFishFrog/gemini-webapi-manager.git#subdirectory=packages/gemini-web2api-manager"
gemini-web2api-manager fetch-upstream
```

Python 3.11+. Пакет залежить від `gemini-vault>=0.2.0,<0.3` і `httpx`.

`gemini-web2api` не встановлюється через pip: його `pyproject` не збирається, бо проєкт складається з кількох модулів верхнього
рівня. Тому код апстріму завантажує команда `fetch-upstream` (закріплений перевірений коміт) у кеш
`$XDG_CACHE_HOME/gemini-web2api-manager/upstream/<коміт>` (за відсутності `XDG_CACHE_HOME` — `~/.cache/…`). Шукається апстрім
у такому порядку: уже імпортований пакет → `--upstream-path` / `GEMINI_WEB2API_PATH` → цей кеш. Код апстріму не змінюється:
під час роботи підмінюються лише кілька його функцій.

Потрібні `GEMINI_MANAGER_KEY` і `vault.bin` з акаунтами (`gemini-vault login-console 1`, див.
[README ядра](../gemini-vault/README.md)).

## Запуск

```bash
gemini-web2api-manager serve --port 8080 --api-key sk-me
gemini-web2api-manager status          # ліміти акаунтів і черга вибору (без запуску шлюзу)
```

| Параметр `serve` | Значення |
| --- | --- |
| `--config FILE` | `config.json` апстріму з необов'язковим блоком `"manager"` |
| `--host`, `--port` | адреса прослуховування; без них і без значень у конфігу діють типові значення апстріму (`0.0.0.0:8081`), тож задавайте їх явно |
| `--api-key KEY` | прийнятний Bearer-ключ; повторюваний |
| `--strategy {sticky,max-remaining}` | політика вибору акаунта |
| `--slots 1,2,3` | використовувати лише ці слоти (типово — усі) |
| `--no-persist-active` | не записувати поточний акаунт у сховище як активний |
| `--upstream-path DIR` | тека з копією gemini-web2api |
| `-v` | докладний журнал |

Базова адреса клієнтів — `http://HOST:PORT/v1`. Поки є хоч один придатний акаунт, шлюз працює; якщо при запуску придатних
акаунтів немає (порожнє сховище, усі сесії відхилено, немає мережі), він завершується з повідомленням і кодом 1.

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8080/v1", api_key="sk-me")
print(client.chat.completions.create(model="gemini-3.6-flash", messages=[{"role": "user", "content": "Привіт"}]))
```

## Конфігурація

Файл — це звичайний `config.json` апстріму (`host`, `port`, `api_keys`, `default_model`, `retry_*`, `temporary_chats` тощо),
до якого можна додати блок `"manager"`. Поля `cookie_file`, `xsrf_token`, `auth_user` ігноруються: сесіями керує сховище.
Приклад — [`deploy/gateway.config.example.json`](../../deploy/gateway.config.example.json).

```json
{"host": "127.0.0.1", "port": 8080, "api_keys": ["sk-me"],
 "manager": {"strategy": "sticky", "refresh_interval": 600, "default_cooldown": 1800}}
```

| Ключ `manager` | Типово | Значення |
| --- | --- | --- |
| `strategy` | `"sticky"` | `sticky` — триматися поточного акаунта, доки він придатний; `max-remaining` — кожен запит на акаунт із найбільшим залишком |
| `refresh_interval` | `600` | як часто (с) оновлювати ліміти, токени й cookie кожного слота |
| `default_cooldown` | `1800` | пауза акаунта (с) після вичерпання ліміту, якщо час скидання вікна невідомий |
| `rate_cooldown` | `60` | пауза (с) після HTTP 429, блокування та помилок авторизації |
| `switch_threshold` | `100` | вважати акаунт вичерпаним, коли використано не менше цього % |
| `persist_active` | `true` | записувати поточний акаунт у сховище як активний |
| `failover_on_empty` | `false` | порожню відповідь вважати відмовою й пробувати інший акаунт |
| `slots` | усі | список слотів, що беруть участь |
| `families` | `pro`, `flash`, `lite`→`flash`, `thinking`→`flash`, `auto`→`flash` | відповідність слів у назві моделі «родинам» квот; ваші записи доповнюють типові |

## Як перемикаються акаунти

**Залишок.** Для кожного акаунта шлюз тримає знімок лімітів і оновлює його кожні `refresh_interval` секунд та одразу після
відмови через ліміт. Залишок рахується по найгіршому з вікон: 5 годин, тиждень і квота моделі потрібної родини (`pro` і
`flash` окремо). Вікно, час скидання якого вже минув, вважається порожнім. Родина визначається за назвою моделі в запиті
(`families`); вичерпаний `pro` не блокує `flash`.

**Вибір.** Придатний акаунт — із дійсною сесією, без активної паузи й із використанням нижче `switch_threshold`.
- `sticky`: шлюз працює з поточним акаунтом, поки він придатний; коли ні — береться акаунт із найбільшим залишком (при рівності
  — давніше використаний, потім менший слот).
- `max-remaining`: кожен запит іде на акаунт із найбільшим залишком.

**Відмова під час запиту.** Якщо відповідь не почалася (до першого відданого токена) і Gemini повернув:

| Ознака | Дія |
| --- | --- |
| `BardErrorInfo [1037]` — ліміт | акаунт ставиться на паузу для цієї родини моделей до скидання вікна (не довше 8 діб), а якщо воно невідоме — на `default_cooldown`; запит повторюється на наступному акаунті; ліміти слота оновлюються негайно |
| `BardErrorInfo [1060]` або HTTP 429 | пауза `rate_cooldown` для всіх моделей, повтор на іншому акаунті |
| HTTP 401/403, помилка xsrf | пауза `rate_cooldown`; сесію оновить фоновий процес; повтор на іншому акаунті |
| інше (мережа, некоректний запит) | помилка віддається клієнту як є |

Клієнт цього не бачить: відповідь буферизується до першого токена. **Після першого відданого токена перемикання вже неможливе**
— помилка іде як є. Для потоку апстрім перед відмовою ще `retry_attempts` разів повторює спробу з кодом 1037 (близько 2 с на
спробу), тому перемикання може тривати на кілька секунд довше.

**Коли ніхто не може відповісти.** Усі акаунти вичерпані — HTTP **429** (`accounts_exhausted`) із заголовком `Retry-After`
(очікуваний час відновлення першого акаунта); немає жодного придатного акаунта (сесії відхилено) — HTTP **503**
(`no_accounts`).

**Стан сховища.** Шлюз *пише* у сховище: зберігає ротовані cookie, знімки лімітів, час останнього використання і, якщо
`persist_active`, активний слот. Тому тека сховища має бути доступна на запис. Слоти, додані чи видалені під час роботи,
підхоплюються без перезапуску (сховище перечитується приблизно раз на 5 с). Зміна проксі слота доходить до запитів
протягом одного циклу оновлення (`refresh_interval`). Після **заміни акаунта в слоті** (`login … --replace`) шлюз потрібно
перезапустити. Сесія, відхилена Google, позначається як прострочена й виводиться з ротації; решта акаунтів працює далі.

## Керування (`/_pool/…`)

| Запит | Дія |
| --- | --- |
| `GET /_pool/status` | стан пулу без секретів: поточний слот, e-mail, придатність, використання, паузи, лічильники, остання помилка |
| `POST /_pool/refresh` | оновити ліміти всіх слотів |
| `POST /_pool/use/N` | зробити слот поточним |
| `POST /_pool/block/N?seconds=600` | вивести слот з ротації |
| `POST /_pool/unblock/N` | зняти паузу зі слота |

Якщо в конфігурації задано `api_keys`, потрібен ключ (`Authorization: Bearer …`); без `api_keys` ці адреси доступні лише з
loopback.

## Діагностика

- `gemini-web2api-manager status` — таблиця акаунтів і порядок вибору для `pro` та `flash`.
- `serve -v` — докладний журнал; рядки `Switching account: A -> B (…)` показують перемикання, `Slot N: quota (…) -> trying another account` — відмови.
- Типові повідомлення: `No usable accounts` — сховище порожнє або сесії відхилено (`login-console SLOT --replace`);
  `Slot N: could not start (…); will retry` — тимчасова помилка запуску сесії, повтор через `refresh_interval`;
  `Could not update vault …` — тека сховища недоступна на запис або змінено ключ.
- Для запуску в Docker і systemd — [`deploy/`](../../deploy/README.md).

## Обмеження

- Один процес шлюзу — один набір налаштувань (апстрім тримає глобальну конфігурацію).
- Класифікація вичерпання ліміту спирається на повідомлення `BardErrorInfo [1037]`; якщо Gemini повертає ліміт іншим
  способом (порожня відповідь), увімкніть `failover_on_empty`.
- Неофіційний веб-клієнт: поведінка Google може змінюватися без попередження.
