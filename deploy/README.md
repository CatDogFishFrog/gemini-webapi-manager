# Розгортання шлюзу на сервері

Шлюз `gemini-web2api-manager serve` — не просто HTTP-сервіс: усередині живе **стан**. Він читає зашифроване сховище
`vault.bin`, **сам його оновлює** (ротовані cookie, ліміти, активний слот), тримає ключ шифрування й сам перемикає акаунти.
Тому в контейнері його запускають лише так, як описано нижче: окрема тека зі сховищем із правом запису, ключ поза образом,
конфіг лише для читання, відповідні uid і коректна зупинка.

| Файл | Призначення |
| --- | --- |
| `Dockerfile` | образ шлюзу: Python 3.12, пакети `gemini-vault` і `gemini-web2api-manager`, код апстріму `gemini-web2api` (завантажується під час збірки) |
| `docker-compose.yml` | запуск контейнера: томи, ключ, користувач, сигнали зупинки |
| `gemini-gateway.service` | unit systemd — той самий шлюз без контейнера |
| `gateway.config.example.json` | приклад конфігурації шлюзу |

## 1. Де що лежить

Структура на хості (шляхи збігаються зі `scripts/manage-vault.sh`):

```text
<репозиторій>/scripts/
├── .env                    GEMINI_MANAGER_KEY=…   (власник — адміністратор, права 600)
├── gateway.config.json     конфіг шлюзу            (монтується в контейнер лише на читання)
└── vault/                  тека сховища            (монтується в контейнер на запис)
    ├── vault.bin           зашифровані акаунти     (права 600)
    └── vault.lock          файл блокування
```

- **Монтується тека `vault/`, а не файл `vault.bin`.** Шлюз записує сховище атомарно: створює тимчасовий файл у тій самій
  теці й підміняє ним `vault.bin`. Підміна файла, змонтованого окремо, у Docker не працює, а теці потрібен дозвіл на запис.
  Це ж стосується блокування (`vault.lock`), яке лежить поруч.
- **Ключ шифрування** — у `scripts/.env`, права `600`. Compose передає його контейнеру через `env_file`. Не передавайте ключ
  аргументом команди (він видимий у `ps`/`docker inspect`) і не вшивайте в образ.
- **Конфіг шлюзу** монтується з `:ro`. API-ключі шлюзу (`api_keys`) задавайте в ньому, а не аргументом `--api-key`:
  аргументи команди видно в `docker inspect` і `ps`.
- **Власник файлів.** Шлюз пише в теку сховища від імені свого процесу, а файл створюється з правами `600`. Тому контейнер
  мусить працювати під тим uid:gid, якому належить тека `vault/` на хості, — інакше шлюз не зможе писати, або адміністратор
  не прочитає файл. У `docker-compose.yml` це `user: "${GATEWAY_UID}:${GATEWAY_GID}"`:

  ```bash
  export GATEWAY_UID=$(id -u) GATEWAY_GID=$(id -g)      # користувач, який керує scripts/vault
  ```
- **Резервні копії:** `vault.bin` і ключ — окремо один від одного. Без ключа файл не відкрити; ключ без файла марний.
- Файлову систему теки сховища слід тримати локальною: на мережевих (NFS/SMB) блокування файлів ненадійне.

## 2. Життєвий цикл

**Перший запуск.** Образ браузера не містить, тому `vault.bin` створюється заздалегідь одним зі способів:

1. на сервері: `./scripts/manage-vault.sh` → «Додати акаунт» (вхід з терміналу; потрібен браузер для входу — пункт меню 10);
2. на іншій машині (наприклад, Windows: `scripts\manage-vault.ps1`) із подальшим копіюванням файла
   (`scp vault.bin сервер:/шлях/scripts/vault/`; ключ має збігатися з ключем сервера);
3. разовим службовим запуском із браузером над тією самою текою й тим самим ключем (див. розділ 4).

**Запуск.**

```bash
cd deploy
cp gateway.config.example.json ../scripts/gateway.config.json     # відредагуйте api_keys
export GATEWAY_UID=$(id -u) GATEWAY_GID=$(id -g)
docker compose up -d --build
curl -H "Authorization: Bearer sk-change-me" http://127.0.0.1:8080/_pool/status
```

Порт опубліковано лише на `127.0.0.1`. Щоб відкрити його назовні, ставте перед ним зворотний проксі з TLS і не вимикайте
`api_keys`.

**Оновлення.** `git pull && docker compose up -d --build` (образ збирається з усього репозиторію; під час збірки шлюз
завантажує код апстріму з GitHub, тож потрібен вихід в Інтернет). Сховище при цьому не чіпається.

**Зупинка.** `docker compose stop` (зачекає до `stop_grace_period`). `init: true` передає шлюзу `SIGTERM`; він закриває сесії,
записує ротовані cookie у сховище й завершується з кодом 0. Те саме робить `systemctl stop`.

Без Docker: `gemini-gateway.service` (відредагуйте шляхи й користувача) → `sudo systemctl enable --now gemini-gateway`.
Правила щодо ключа (`EnvironmentFile`, права `600`), теки сховища (`ReadWritePaths`) і власника ті самі.

## 3. Керування акаунтами в запущеному шлюзі

Усі операції змінюють `vault.bin`. Шлюз перечитує сховище приблизно раз на 5 секунд.

| Операція | Команда | Чи підхопить працюючий шлюз |
| --- | --- | --- |
| Додати акаунт у вільний слот | `login-console SLOT` | так, без перезапуску |
| Видалити акаунт | `remove SLOT` (`--revoke` — ще й вийти на боці Google) | так: слот закривається й зникає з пулу |
| Замінити акаунт у слоті (повторний вхід, нова сесія) | `login-console SLOT --replace`, або `remove` + `login` | так: шлюз закриває стару сесію і відкриває нову, статистика слота починається з нуля |
| Змінити проксі слота | `proxy SLOT URL` | так: слот відкривається заново з новим проксі |
| Змінити активний слот | `use SLOT` | у sticky-режимі шлюз сам пише поточний акаунт у сховище; для негайного перемикання скористайтеся `POST /_pool/use/N` |
| Змінити конфіг шлюзу (`gateway.config.json`) | редагування файла | ні — перезапуск |
| Змінити ключ шифрування | див. нижче | зупинка → зміна → запуск |

**Зміна ключа шифрування.** Працюючий шлюз тримає старий ключ у пам'яті: якщо перешифрувати файл під ним, шлюз не впаде,
але перестане зберігати ротовані cookie й не побачить змін сховища (у журналі повторюватимуться `Could not update vault`).
Порядок завжди такий: **зупинити шлюз → перешифрувати сховище → оновити ключ у `scripts/.env` → запустити шлюз**.

## 4. Де виконувати адміністративні команди

- Команди, що не потребують браузера (`list`, `use`, `usage`, `remove`, `proxy`), можна виконувати в працюючому контейнері:

  ```bash
  docker compose exec gemini-gateway gemini-web2api-manager list
  docker compose exec gemini-gateway gemini-web2api-manager usage
  ```
  (контейнер уже працює під потрібним uid і має ключ у середовищі).
- Вхід (`login-console`) потребує браузера, якого в образі немає. Виконуйте його на хості (`scripts/manage-vault.sh`) або
  в окремому службовому запуску з браузером **над тією самою текою `scripts/vault` і з тим самим ключем** і тим самим uid.
- Стан пулу — `GET /_pool/status` та `gemini-web2api-manager status`; опис — у
  [README пакета](../packages/gemini-web2api-manager/README.md).

## 5. Конфігурація шлюзу

`gateway.config.example.json` — звичайний `config.json` апстріму з блоком `manager`:

| Поле | Значення |
| --- | --- |
| `host`, `port` | адреса прослуховування; в образі перекриваються аргументами `--host 0.0.0.0 --port 8080` |
| `api_keys` | список прийнятних Bearer-ключів; без нього адмін-адреси `/_pool/*` доступні лише з loopback, а `/v1` — без автентифікації |
| `default_model` | модель за замовчуванням |
| `manager.strategy` | `sticky` або `max-remaining` |
| `manager.refresh_interval` | період оновлення лімітів і cookie, с |
| `manager.default_cooldown` | пауза акаунта після ліміту, якщо час скидання невідомий, с |
| `manager.persist_active` | записувати поточний акаунт у сховище |

Повний перелік полів `manager` — у [README пакета](../packages/gemini-web2api-manager/README.md#конфігурація).

## 6. Приклад повного запуску

```bash
git clone https://github.com/CatDogFishFrog/gemini-webapi-manager.git && cd gemini-webapi-manager
./scripts/manage-vault.sh login-console 1 --email first@gmail.com      # створить scripts/.env, vault/ і vault.bin
./scripts/manage-vault.sh login-console 2 --email second@gmail.com
cp deploy/gateway.config.example.json scripts/gateway.config.json      # змініть api_keys
cd deploy && export GATEWAY_UID=$(id -u) GATEWAY_GID=$(id -g) && docker compose up -d --build
```

Клієнт — `OpenAI(base_url="http://127.0.0.1:8080/v1", api_key="<ключ з api_keys>")`. Коли в першого акаунта закінчиться
ліміт, шлюз сам переведе запити на другий.
